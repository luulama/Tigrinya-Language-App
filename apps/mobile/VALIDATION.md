# iOS preparation verification

The separate mobile slice is prepared and its bundled browser flows pass. The native bridge type-checks against the real iOS SDK and pinned Capacitor frameworks. A complete Xcode app build and simulator/device launch remain blocked by the installed Xcode environment's missing iOS platform component. No signing, installation, database access, deployment, Git commit, push or Apple submission was performed.

## Current continuation status on 21 November 2026

The selected Xcode is 26.3, its simulator/device SDK is 26.2, first-launch status is ready and the official `-downloadPlatform` command is available. `simctl list runtimes -j` returned an empty runtime list. Both simulator and unsigned hardware-target builds were attempted; both stop before app compilation with **iOS 26.2 is not installed**. An SDK being present is insufficient to establish Xcode platform readiness.

The Mac has approximately **4.7 GiB available**. Apple's official simulator catalogue lists **8,388,683,973 bytes (about 7.8 GiB)** for the stable iOS 26.2 arm64 download, before expansion/installation. A download would therefore not fit. No runtime download was started and no user files were removed to make room. The new installer preflight requires 30 GiB free as a project-specific safety margin; that is not an Apple-published requirement or a guarantee for future downloads. Its blocked exit is the intended safe behavior on this Mac.

New commands:

- `ios:doctor` reads tool/runtime/disk/configuration status and lists missing owner choices. It never opens Apple Accounts or Keychain, starts a backend, signs, downloads or accepts a licence. Its nonzero status reflects the actual missing runtime/identity/team.
- `ios:install-runtime` validates Xcode first-launch status, SDK version, runtime-query success, architecture and disk capacity before invoking Apple's version-matched command. It refuses this Mac's low-space condition. An existing runtime makes it a no-op.
- `ios:build:device` targets `iphoneos` and `generic/platform=iOS`, uses its own generated DerivedData and explicitly disables signing. This verifies that a hardware-target build does not bypass the current platform blocker. It does not install on a phone.

The continuation snapshot comparison covered **388 existing source files outside `apps/mobile`**, including previously uncommitted web/mascot work. All remain byte-for-byte unchanged. Only mobile-target source/configuration/documentation was edited or added; Git's index remains unchanged. New helper/configuration files pass formatting and syntax checks.

`device.example.json` now gives the owner two intentionally empty identity fields. An optional ignored `device.local.json` accepts only `appId` and `appName`; it preserves actual owner choices across terminal sessions without silently enabling networking. Environment identity overrides remain supported. API, database, signing and secret fields are rejected in that file. It is excluded from generated mobile assets. Signing team selection stays in Xcode; no identity or team was chosen for the owner.

The [Swedish iPhone setup guide](IPHONE_SETUP.sv.md) documents the exact component installation, local identity file, Xcode Apple Accounts/Signing & Capabilities, cable pairing, Developer Mode, Run action and device-only checks. It distinguishes unsigned compilation from signed device installation, and private test audio from approved language recordings.

## Browser and visual coverage

The mobile tests exercise all six home entry routes without external requests, original Fidäl model/Unicode input/freehand drawing, the word path's first practice/revisit navigation, both ten-game catalogues and game launches, the twenty-story library and full reader, offline/no-API behavior, external-link blocking, unsupported recording, small 320-pixel layouts, reduced motion and JavaScript-disabled entry HTML.

The native recording transport test uses a locally generated, explicitly labelled 0.1-second silent AAC fixture. It tests the adapter, valid clip decoding/playback controls, stop/cancel and deletion, without pretending to capture native speech. Permission and lifecycle unit tests use isolated transports and synthetic bytes. They do not exercise Apple's actual permission dialog, physical microphone, speaker routing or interruptions.

Visual inspection covered desktop and phone home screens, phone voice practice and the existing Fidäl lesson in WebKit. No horizontal overflow, broken mascot assets, clipped navigation or script-rendering errors were observed in these views. These tests cover mobile entry/integration behavior; they do not replay every lesson and every game to completion, establish native-language correctness, or prove learning efficacy. The root's full 278-case browser suite from the preceding bear work was not rerun for this isolated target; this task ran the separate sixteen-case mobile suite and the existing source/unit/build checks.

The first mobile browser run had four test failures: the writing test tried to fill an input inside its unopened details panel, and the recording fixture contained invalid media bytes. Opening the real text-practice panel and replacing the fixture with valid generated silence corrected those test failures. Both final browser engines pass. A stale-permission race in the new browser recording adapter was also prevented and is covered by the final unit tests.
